# 시스템 구성

> 2026-10-25 재계획에 따른 새 구조입니다. 휴대폰 쪽은 Android 앱 대신 모바일 웹으로 만듭니다. 통신 형식은 초안이며 10/26에 팀이 확정합니다. 이전 구조(Pi 단독, L3/L4 두 프로세스)는 저장소의 기존 시험 구현에 남아 있습니다.

모든 기기는 시연장의 같은 공유기(또는 핫스팟)에 연결합니다. 서버 PC는 공유기에서 고정 IP를 받도록 설정해 클라이언트가 같은 주소로 접속하게 합니다.

휴대폰 쪽은 앱을 설치하지 않고, 서버가 제공하는 웹페이지를 휴대폰 브라우저로 엽니다. 휴대폰 브라우저는 HTTPS 페이지에서만 카메라를 열 수 있으므로 서버는 HTTPS(`https://`, `wss://`)로 동작해야 합니다. 시연용으로는 mkcert 같은 도구로 인증서를 만들고, 그 인증 기관을 휴대폰과 Pi에 설치해 경고 없이 접속하게 합니다.

## 구성 요소

| 구성 요소 | 역할 | 기술 |
| --- | --- | --- |
| 중앙 서버 | 장치 연결 관리, 영상 분석, 낙상 판정, 음성 인식, 이벤트 기록, 경보 전달, 웹페이지(보호자·카메라·키오스크) 제공 | Python, FastAPI(제안), Ultralytics YOLO-Pose, faster-whisper, SQLite |
| Pi 현장 단말 | 카메라 프레임 전송, 서버 요청 시 안내 음성 재생과 응답 녹음, 현장 화면(Chromium 키오스크) | Python, OpenCV, sounddevice |
| 보호자 화면 (`/guardian`) | 휴대폰 브라우저에서 현재 상태, 경보 수신(소리·진동), 이벤트 기록 조회 | HTML·JavaScript, WebSocket, Vibration API, Wake Lock API |
| 카메라 감지 화면 (`/camera`) | 휴대폰 카메라 프레임을 서버로 전송해 하나의 감지 장치로 동작 | HTML·JavaScript, getUserMedia, canvas로 JPEG 변환 |
| 현장 화면 (`/kiosk`) | Pi 디스플레이에서 상태 표시와 '괜찮아요' 버튼 | HTML·JavaScript (Chromium 키오스크) |

## 처리 흐름

1. Pi와 휴대폰(카메라 감지 화면)은 각자 `device_id`로 서버에 접속해 JPEG 프레임을 초당 약 10장 보냅니다.
2. 서버는 장치별로 따로 자세 추정, 특징 계산, 상태 머신을 돌립니다.
3. 하강 속도 피크 뒤 누운 자세가 일정 시간(T1) 이어지면 그 장치에 낙상 의심 이벤트를 만듭니다.
4. Pi 장치면 서버가 Pi에 음성 확인을 요청합니다. Pi는 안내 음성을 재생하고 몇 초 녹음해 서버로 보냅니다. 휴대폰 장치의 확인 방법은 아직 정하지 않았습니다([PROJECT_PLAN.md](PROJECT_PLAN.md) '확인이 필요한 결정').
5. 서버는 Whisper로 인식한 문장을 키워드로 분류합니다. '괜찮다'면 해제, 도움 요청·무응답·장치 오류면 경보로 바꿉니다.
6. 경보는 열려 있는 보호자 화면 전체에 전달합니다. Pi 현장 화면의 '괜찮아요' 버튼이나 보호자 화면에서 경보를 끝냅니다.

## 상태 흐름

장치별 감지 상태: 정상 → 하강 감지 → 낙상 의심 (이벤트가 끝날 때까지 유지)

이벤트 상태: 음성 확인 중 → 해제 또는 경보 → (버튼으로) 종료

같은 장치에서 진행 중인 이벤트가 있으면 새 이벤트를 만들지 않습니다. 이벤트가 끝나면 그 장치의 감지 상태를 정상으로 되돌려 다시 감시합니다.

## 통신 형식 초안 (10/26 확정)

| 연결 | 방향 | 내용 |
| --- | --- | --- |
| `WS /ws/camera?device_id=pi-1` | 클라이언트 → 서버 | 바이너리 메시지 1개 = JPEG 프레임 1장 (640×480, 품질 70 안팎) |
| | 서버 → 클라이언트 | `{"type": "voice_check", "event_id": 12}` 음성 확인 요청 (Pi만) |
| | 서버 → 클라이언트 | `{"type": "state", "state": "NORMAL" \| "SUSPECT" \| "ALARM"}` 상태 변경 |
| `POST /api/events/{id}/voice` | Pi → 서버 | 응답 녹음 wav (16kHz, 모노) |
| `WS /ws/guardian` | 서버 → 보호자 화면 | 접속 직후 `{"type": "snapshot", "devices": [...], "active_events": [...]}`, 이후 `{"type": "device", ...}`, `{"type": "event", ...}` |
| `GET /api/events?limit=N` | 보호자 화면 → 서버 | 최근 이벤트 기록 |
| `POST /api/events/{id}/clear` | 현장 화면·보호자 화면 → 서버 | '괜찮아요' 버튼, 경보 종료 |
| `GET /kiosk?device_id=pi-1` | Pi 브라우저 | 현장 화면 |
| `GET /guardian` | 휴대폰 브라우저 | 보호자 화면 |
| `GET /camera?device_id=phone-1` | 휴대폰 브라우저 | 카메라 감지 화면. 같은 `/ws/camera`로 프레임 전송 |

보호자 화면이 다시 연결되면 `snapshot`으로 진행 중인 경보를 다시 받습니다. 연결이 끊긴 동안 생긴 경보를 놓치지 않기 위해서입니다.

## 장애 처리

| 상황 | 처리 |
| --- | --- |
| 서버 연결 끊김 | Pi 클라이언트와 웹페이지는 몇 초 간격으로 재연결. 현장 화면과 보호자 화면에 '감지 중단' 표시 |
| 카메라 프레임이 끊김 | 서버가 장치별 마지막 프레임 시각을 보고 '카메라 응답 없음'을 보호자 화면과 현장 화면에 표시 |
| 녹음 실패·인식 실패 | 확인할 수 없으므로 경보로 처리 |
| 서버 재시작 | 끝나지 않은 이벤트는 '중단'으로 기록. 경보 상태였던 이벤트는 다시 연결된 보호자 화면에 계속 보여 줌 |

## 데이터와 개인정보

- 카메라 프레임은 같은 네트워크 안의 서버로만 보내고, 서버는 메모리에서 처리한 뒤 버립니다. 원본 영상은 저장하지 않습니다.
- 응답 녹음은 인식이 끝나면 지웁니다. 기본은 분류 결과(괜찮음·도움 요청 등)만 저장합니다.
- 이벤트 기록: 장치, 발생 시각, 판정 시점의 특징값, 음성 확인 결과, 경보 여부, 종료 방법과 시각.
- 테스트 영상 촬영은 대상자 동의를 받고, 보관 기간과 접근 권한을 정한 뒤 진행합니다.
