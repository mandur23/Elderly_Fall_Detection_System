# 시스템 구성 초안

> 구성은 프로젝트 계획서에 따른 제안이며, 모델과 알림 방식은 구현·검증 후 확정합니다.

## 처리 흐름

~~~mermaid
flowchart LR
    A[실내 카메라] --> B[영상 입력 및 전처리]
    B --> C[인체 상태 분석]
    C --> D{낙상 의심?}
    D -- 아니요 --> E[상태 표시]
    D -- 예 --> F[음성 상태 확인]
    F --> G{확인 결과}
    G --> H[이벤트 기록]
    G --> I[필요 시 알림]
    H --> E
    I --> E
~~~

## 구성 요소

| 구성 요소 | 역할 | 결정 상태 |
| --- | --- | --- |
| 카메라 입력 | 실내 영상 수집 | 카메라 종류 확정 전 |
| 영상 분석 | 자세·움직임 분석과 낙상 의심 판정 | 모델·판정 기준 비교 예정 |
| 음성 입출력 | 의심 상황 안내와 상태 확인 | 문구·응답 방식 결정 전 |
| 이벤트 관리 | 상태 변화와 처리 결과 기록 | 저장 형식 결정 전 |
| 알림 | 보호자 또는 관리자에게 상황 전달 | 채널·수신자 설정 방식 결정 전 |
| 사용자 화면 | 현재 상태와 이벤트 표시 | 화면 구성 설계 예정 |

## 상태 흐름

정상 감시 → 낙상 의심 → 음성 확인 → 상황 해제 또는 알림

상태 전환 조건과 대기 시간은 테스트 결과를 보고 정합니다. 동일한 상황에서 알림이 반복되는 문제와 사용자가 정상 상태임을 확인했을 때의 해제 절차도 구현 시 정의합니다.

## 현재 시험 구현

아래는 흐름을 확인하기 위해 고른 시험 구현이며, 비교·검증 후 바뀔 수 있습니다.

| 구성 요소 | 시험 구현 | 비고 |
| --- | --- | --- |
| 영상 분석 | MediaPipe Pose 또는 YOLO-Pose로 관절 추정 → 몸통 각도·종횡비·하강 속도(0.3초 구간) 계산 | 하강 속도 피크 후 누운 자세(또는 사람이 안 보임)가 T1 동안 이어지면 낙상 의심. 기준값 근거는 [성능 평가 기록](EVALUATION.md) |
| 음성 입출력 | 미리 녹음한 안내 음성 재생 후 Vosk 오프라인 인식(자유 인식 + 응답 문구 제한 인식), 키워드 분류 | 도움 요청·부정 표현("안 괜찮아요")을 먼저 검사. 문구 제한 인식은 신뢰도가 높을 때만 사용. 무응답·장치 오류는 경보 |
| 이벤트 관리 | SQLite (`data/fall_events.db`) | 인식 문장 원문은 기본 저장 안 함 |
| 알림 | 텔레그램 봇 텍스트 메시지 | 실패 시 재시도, 지연 전송 시 원래 발생 시각 표시 |
| 사용자 화면 | 로컬 웹 페이지(Chromium 키오스크) | 상태, 알림 전송 결과, 장치 문제 표시 |

L3 상태: 정상 → 하강 감지 → 낙상 의심(L4가 이벤트를 끝낼 때까지 유지)
L4 상태: 정상 → 음성 확인 중 → 해제 또는 경보 → (화면 버튼으로) 정상

한 이벤트에서 경보 알림은 한 번만 보냅니다. 경보 후 화면 버튼으로 해제하면 이미 보낸 알림에 대해 해제 메시지를 보내고, 아직 전송하지 못한 알림은 취소합니다.

L4가 재시작되면 해제되지 않은 경보는 다시 경보 화면으로 띄우고, 전송 도중 끊긴 알림은 다시 보냅니다. 음성 확인 도중 끊긴 이벤트는 '처리 중 재시작됨'으로 기록합니다.

## 데이터 흐름과 운영 시 고려사항

- 영상과 음성은 감지와 상태 확인에 필요한 범위에서 사용합니다.
- 이벤트 기록에는 발생 시각, 판단 상태, 확인 결과, 알림 결과 등 필요한 최소 정보를 담는 방향으로 설계합니다.
- 원본 영상·음성의 저장 여부, 보관 기간, 접근 권한은 실제 촬영 전에 결정해야 합니다.
- 외부 알림은 네트워크 장애 시 실패를 표시하고 재시도 여부를 정할 수 있도록 설계합니다.
